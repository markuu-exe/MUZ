# Team Coordination and Handoff Guide

This guide connects the four member guides. It lists who waits on whom, the shared contracts, the shared-file rules, the handoff messages, and the evidence needed for Done.

---

## 1. Communication routine (SPMP §8)

| When | What | Who |
|---|---|---|
| 09:15–09:30 daily | Post your status in the team chat (format below) | Everyone |
| On any blocker longer than half a day | Message A | Anyone |
| On any contract change | Post the proposal **before** coding, then wait for A's OK | Proposer |
| When a PR opens | Post the link and tag the reviewer | Author |
| When a PR merges | A posts "merged T-xx" so anyone waiting can start | A |
| At each checkpoint (IC-0…IC-4, RC, Release) | A posts pass/fail per item and updates Jira | A |

**Daily status format:**
```
Yesterday's progress:
Today's target:
Current blocker:
Jira ticket:
Expected deliverable:
```

## 5. Evidence required before a Jira issue is marked Done

Only A moves issues to Done, after merging and checking the evidence below.

1. **The PR**, merged into `main` with the reviewer's approval.
2. **A green CI run** covering `npm test`, `npx tsc -p tsconfig.json`, `npx vite build`, `npm run seed:lessons:check` and the size check (from D2 onward).
3. **The acceptance checklist** from the member guide, each line ticked with its evidence:

   | What is being proved | Evidence |
   |---|---|
   | Logic | Test names, plus the pasted test output |
   | UI | Before/after screenshots |
   | Supabase behaviour | A staging note: date, test account, table rows seen |
   | Performance | The numbers from the T-19 report |
   | Privacy | The T-21 report |

4. **"Not verified:"** a line stating anything that was not checked.
5. **Reopened issues** (KAN-228, KAN-229, KAN-10, KAN-11; KAN-258 goes to In review) close only with this same evidence.

Static code review alone never counts as Done.

## 7. Escalation

1. **Blocked for more than half a day.** Tell A. A pairs with you for 30 minutes.
2. **Task more than 1 day late.** A applies the contingency from the master schedule §5 and posts it.
3. **A requirement must change.** Write a change-control note (SPMP 3.3: description, reason, affected requirements, effort, schedule, testing, documentation). A decides with the team, and asks the adviser if a requirement would be dropped.
4. **Data loss or a security problem.** Tell A immediately. It is treated as P0.
